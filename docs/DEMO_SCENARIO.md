# Demo Scenario

## Purpose

This document defines a polished, repeatable demo scenario for Bookforge interviews.

The goal is to show Bookforge as an end-to-end market microstructure project that combines:
- a C++20 matching engine,
- deterministic replay,
- feature extraction,
- Python research workflows,
- and an inspection layer through the API and dashboard.

The demo is designed to be credible, compact, and easy to run live.

## Audience

This scenario is best suited for:
- quant SWE interviews,
- quant research interviews,
- market data / infrastructure interviews,
- systems interviews where practical architecture matters.

## Demo objective

The objective is to show that Bookforge is not just a toy order book.

By the end of the demo, the audience should understand that the project can:
1. replay historical or synthetic event streams deterministically,
2. maintain a consistent price-time-priority book,
3. export structured market-state features,
4. support downstream analysis in Python,
5. and expose inspectable outputs through an API and dashboard.

## Demo storyline

The shortest useful storyline is:

1. Start from replayable market events.
2. Feed them into a deterministic replay pipeline.
3. Show that the matching engine updates book state consistently.
4. Export features such as spread, mid-price, depth imbalance, and OFI.
5. Show how those outputs become research-ready datasets and dashboard views.
6. Close with benchmarks, tests, and engineering controls.

This keeps the demo focused on one question:

**How do raw market events become a reproducible research and systems workflow?**

## What to show

### 1. Repository framing

Start with a short explanation:

> Bookforge is a hybrid C++ and Python market microstructure project.  
> The C++ side owns the matching engine, replay, and performance-sensitive paths.  
> The Python side handles data workflows, evaluation, and lightweight serving for inspection.

Keep this section under one minute.

### 2. Architecture

Open `docs/ARCHITECTURE.md` and show:
- the end-to-end replay pipeline,
- the core engine structure,
- the replay control flow.

Narrate the boundaries clearly:
- `HyperliquidCsvReader` parses input,
- `ReplayRunner` controls sequencing,
- `IReplayAdapter` decouples replay from execution,
- `HyperliquidMatchingEngineAdapter` translates events,
- `MatchingEngine` and `OrderBook` own the market state.

### 3. Deterministic replay

Explain that replay is deterministic and bounded.

Highlight:
- the same input fixture produces the same ordered replay,
- replay can be bounded with offsets and max event counts,
- this makes tests, benchmarks, and debugging more reliable.

If useful, mention both:
- historical-style fixtures,
- and synthetic fixtures generated by `tools/generate_replay_fixture.py`.

### 4. Feature export

Show the feature export path as the bridge from systems code into research.

Call out a few features:
- spread,
- mid-price,
- L1 depth,
- depth imbalance,
- OFI,
- rolling context features.

The point here is not model sophistication. The point is that the system exports structured state cleanly enough to support experiments.

### 5. Python research layer

Explain that Python is intentionally downstream of the C++ core.

Use a short summary:
- load exported feature CSVs,
- construct datasets,
- generate labels,
- train a baseline model,
- run chronological or walk-forward evaluation.

Frame this as:
> The matching logic stays in C++, while Python makes experimentation faster.

### 6. Dashboard / API

If the dashboard is running cleanly, use it.

Show:
- replay summary,
- feature sample views,
- charts for spread, mid-price, L1 depth, and imbalance.

If the dashboard is not running, use the API or exported CSVs instead. The demo should never depend on the riskiest component.

### 7. Benchmark and test credibility

End with engineering proof:
- GoogleTest coverage,
- Pytest coverage,
- replay and order-book benchmarks,
- CI and formatting controls.

This is where you show that the project is not just visually polished; it is tested and benchmarked.

## Suggested live flow

## Recommended commands

### Build the project

#### Windows PowerShell
```powershell
cmake -S . -B build
cmake --build build --config Release --parallel
```

### Run C++ tests

#### Windows PowerShell
```powershell
ctest --test-dir build -C Release --output-on-failure
```

### Run Python tests

#### Windows PowerShell
```powershell
$env:PYTHONPATH = "python"
python -m pytest tests/python -q
```

### Generate a replay fixture

#### Windows PowerShell
```powershell
python tools\generate_replay_fixture.py --events 10000 --base-price 100.00 --output tests\fixtures\hyperliquid_replay_fixture_large.csv
```

### Run replay benchmark

#### Windows PowerShell
```powershell
.\build\bench\Release\benchmark_replay.exe
```

### Export features

#### Windows PowerShell
```powershell
.\build\Release\feature_export_main.exe --input data\btc_orders_sample_2025-12-15-12.csv --output output\features.csv --symbol BTCUSDT.P --snapshot-depth 10 --imbalance-depth 10 --ofi-depth 10 --rolling-window 50
```

### Launch API

#### Windows PowerShell
```powershell
$env:PYTHONPATH = "python"
uvicorn api.main:app --reload --port 8010
```

### Launch dashboard

#### Windows PowerShell
```powershell
cd dashboard
npm install
npm run dev
```

## Demo script

Use this as a short speaking script:

> Bookforge is a C++20 limit-order-book and replay project with a Python research layer on top.  
> The core idea is to keep matching and replay mechanics in C++, then export structured state into Python for experiments and evaluation.  
> The replay pipeline is deterministic, which makes testing, benchmarking, and debugging much easier.  
> From that replayed state, the project derives features like spread, mid-price, depth imbalance, and OFI.  
> Those outputs then feed Python-side dataset building, baseline modeling, and a lightweight inspection layer through FastAPI and React.  
> What I wanted to show here is not just a matching engine, but a full path from market events to reproducible research and presentation.

## Interview-safe defaults

If time is short:
- show architecture,
- run one benchmark,
- show one exported feature file or API response,
- mention tests and CI,
- stop there.

If something breaks live:
- skip the dashboard first,
- fall back to docs, benchmark output, and CSV artifacts,
- keep the story focused on deterministic replay and system boundaries.

## Do not over-claim

Avoid saying:
- this is a production trading system,
- this exactly replicates exchange behavior,
- this fully models market impact,
- this proves trading profitability.

Safer phrasing:
- educational but serious,
- deterministic and replayable,
- useful for systems and research experimentation,
- designed to be extended.
